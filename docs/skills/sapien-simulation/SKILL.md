# SAPIEN Simulation

Use this skill when creating, refactoring, or reviewing SAPIEN simulation environments.

## Required behavior

1. Read `docs/gpu-workflows.md` before editing SAPIEN simulation code.
2. For API lookup, use the compact agent tables under `docs/api/README.md` before guessing names/signatures.
3. When installing SAPIEN for examples, validation, or containers, use the fork's GitHub release wheels from `https://github.com/yolkarian/SAPIEN/releases`; do not install SAPIEN from PyPI.
4. Use SAPIEN GPU PhysX and GPU APIs for parallel simulation.
5. Preserve initialization order: configure PhysX (including `PhysxSceneConfig.num_scenes` and `with_shared_scene`, which are read once when the GPU system is constructed and frozen there), create systems, create builders, create scenes, mark the shared scene and apply any scene offsets, build bodies, add lights, call `gpu_init()`, initialize GPU buffers, then initialize viewer/sensors/rendering.
6. For many identical URDF robots, parse the URDF once, cache the builder, and reuse it with `builder.set_scene(scene)` plus a restored initial pose before each `builder.build()`. For kinematics-only or IK-only workflows, set `loader.load_visuals = False` and `loader.load_collisions = False` when geometry is unnecessary.
7. Prefer PhysX GPU scene environment IDs for multi-env isolation. There are two disjoint modes, declared on `PhysxSceneConfig` before creating `PhysxGpuSystem` and frozen at construction:
   - Managed mode (`num_scenes = N`): SAPIEN is the sole assigner. Each Scene gets a unique ID on first use via `Scene.get_or_assign_environment_id()` or when a body is added; `N` is a hard cap on ordinary scenes held at once, and `Scene.set_environment_id()` raises. Bit counts are derived: `(0, 0, b)` without a shared scene, `(b, b, b)` with one.
   - Manual mode (`num_scenes` unset): SAPIEN numbers nothing; an unnumbered scene is environment 0. `Scene.set_environment_id(env_id)` numbers scenes, only before the scene gets any actor/articulation; `env_id` is the raw, unshifted ID. `get_or_assign_environment_id()` raises. Duplicates are legal and meaningful — giving several Scenes the same ID puts them in one environment so they collide, which auto-assignment cannot express.
   `with_shared_scene = True` works in both modes: it enables `Scene.set_shared_environment()` on the one shared scene (call before it gets a body; it reports `environment_id == -1` and costs no `num_scenes` slot, releasing any ID it had been assigned), widens all non-zero bit counts to be equal, and shifts every ID into a band overlapping the shared object. `Scene.environment_id` is the raw, unshifted ID SAPIEN's filter shader compares; `PhysxGpuSystem.get_broadphase_environment_id(scene)` is the value `PxActor::setEnvironmentID` receives, with the band offset applied only there — without a shared scene the offset is 0 so the two match, with one they differ.
   Without environment IDs every scene is environment 0 and only `set_scene_offset()` keeps scenes apart, which cannot separate infinite planes: add `scene.add_ground()` once for all scenes, not once per scene (per-scene planes touch every environment's bodies, overflow PhysX's contact buffer, and bodies fall through the ground).
8. Create `sapien.render.RenderSystem` only when viewer, sensors, or offscreen rendering need it; do not create it for pure physics.
9. For an interactive PhysX GPU Viewer, initialize GPU PhysX first, use automatic direct/staged pose transport, call `viewer.apply_interactions()` immediately before every physics substep that may consume Viewer commands, call `viewer.update_render()` after each displayed state, and then call `viewer.render()`. Reserve `PhysxGpuSystem.sync_poses_gpu_to_cpu()` for explicit CPU debugging or Viewer `cpu-debug`. For offscreen capture, follow the explicit `RenderSystemGroup` lifecycle: construct, `set_cuda_poses(...)`, `create_camera_group(...)`, then one `gpu_init()` that prepares resources, takes the one-time CPU snapshots, seeds cuda-mode camera pose rows, and seals transform ownership. Configure each free camera's pose mode with `RenderCameraGroup.set_pose_mode(camera, mode)` after `create_camera_group()` and before `gpu_init()`: `'static'` (default) snapshots the CPU pose once at `gpu_init()` and never moves; `'cpu'` keeps the CPU pose authoritative and uploads it per `update_render()` for host-driven follow/anchor cameras; `'cuda'` allocates a group-owned CUDA pose row (`cuda_poses`) seeded from the CPU pose and moved via GPU writes or `set_cuda_pose`. Mounted cameras on PhysX GPU bodies are auto-attached and cannot be configured. Per frame, move a cuda-mode free camera by writing its `cuda_poses` row or `set_cuda_pose` then one `update_render()`; move a cpu-mode camera with `set_local_pose` then one `update_render()`.
10. In long-lived Python processes, tear down each job deterministically: release owner-tracked `CudaArray` handles and derived DLPack consumers (`torch.from_dlpack(x)`, `jax.dlpack.from_dlpack(x)`, `.torch()` / `.jax()` / `.cupy()` / `.dlpack()`); close Viewers and `RenderSystemGroup` objects; close every `Scene`; close detached `RenderSystem` and `PhysxSystem` objects; then require `sapien.can_shutdown()` (diagnose failures with `sapien.get_live_resources()`) before `sapien.shutdown()`. Top-level shutdown preflights without partial mutation and releases render before PhysX. These `close()` calls are terminal and idempotent; use `Scene.clear()` only when reusing that Scene. The closeable lifecycle objects also support context managers.
11. Cache SAPIEN CUDA tensor views (Torch/CuPy) and GPU indices once after `gpu_init()`; use cached indices for batched access, then release those views before job teardown. JAX is the exception: take `jax.dlpack.from_dlpack(system.cuda_*)` after every fetch (zero-copy) so JAX gets the stream dependency, copy what must outlive the next fetch inside the jitted step, never donate imported arrays, and write results back with `system.cuda_*.copy_from(jax_array)` before the apply. `CudaArray.__dlpack__(stream=...)` orders the consumer's stream after the system's stream; `copy_from` and indexed inputs order the system's stream after the producer; `PhysxGpuSystem.gpu_wait_for(array)` adds that wait alone. After manually applying articulation root/qpos state, `gpu_update_articulation_kinematics()` updates PhysX internal kinematics but invalidates the public articulation-link pose rows; call `gpu_fetch_articulation_link_pose()` before any read or `RenderSystemGroup.update_render()` that consumes `cuda_rigid_body_data`. Rigid-body rows written directly to that buffer do not refresh articulation-link rows.
12. For indexed GPU APIs, allowed selected-index argument types are `sapien.CudaArray`, `__dlpack__` producers (CUDA `torch.Tensor`, `jax.Array`, `cupy.ndarray`; the system's stream waits for the producer through the DLPack handshake, for Torch call inside the producing stream's context), or CUDA-array-interface objects such as Numba CUDA device arrays (their v3 `stream` entry is waited on). They must wrap 1D contiguous CUDA `int32` buffers on the same CUDA device as the PhysX system and contain SAPIEN `gpu_index` values; NumPy arrays, Python lists, CPU tensors, `int64` tensors, non-contiguous views, and cross-device arrays are invalid. SAPIEN keeps the producer alive until its stream has used the buffer. Values are range-checked by default: an out-of-range or negative entry, or more entries than the rigid-dynamic/articulation count, raises `RuntimeError` before anything is applied. That value check synchronizes the SAPIEN CUDA stream once per indexed call; prefer the non-indexed overloads when every row changed, and for throughput-critical loops with trusted indices set `PhysxSceneConfig.gpu_index_validation = False` before creating the `PhysxGpuSystem` (frozen at construction; host-side checks still run, out-of-range values become undefined behavior).
13. Contact impulse queries synchronize by default. With `synchronize=False`, consume `query.cuda_impulses` on the stream set by `gpu_set_cuda_stream`, or call `gpu_wait_contact_queries()` before host/cross-stream access. `step()` / `step_start()` / PhysX `gpu_init()` wait for outstanding asynchronous queries before invalidating contact pointers; reinitialization also invalidates the cached contact snapshot.
14. SAPIEN has no IK solver. Exposed PhysX GPU buffers after `gpu_init()`: `cuda_articulation_link_data`, `cuda_articulation_jacobian`, `cuda_articulation_jacobian_shape`.
15. For Docker/containerized SAPIEN GPU rendering, configure NVIDIA Vulkan/EGL ICD discovery explicitly: inject minimal NVIDIA ICD JSON files when needed, set `VK_ICD_FILENAMES=/etc/vulkan/icd.d/nvidia_icd.json`, and rely on NVIDIA Container Toolkit for the actual driver libraries instead of installing drivers in the image.
16. Pre-bake the PhysX GPU runtime library into SAPIEN Docker images so `sapien.physx.enable_gpu()` does not download `physxgpu-linux-clang.zip` on every fresh container start. After SAPIEN is installed, derive `PHYSX_VERSION` from `sapien.physx.version()`, extract the matching release zip into `$HOME/.sapien/physx/<PHYSX_VERSION>/`, and verify the nested `libPhysXGpu_64.so`. Do not call `enable_gpu()` during `docker build` because it also loads `libcuda.so` and needs the runtime GPU driver. See `docs/gpu-workflows.md` for the exact Dockerfile snippet.
17. A single GPU needs no device argument: `PhysxGpuSystem()` uses the only visible GPU, and single-GPU code is unchanged by multi-GPU support. For multiple GPUs, use one `PhysxGpuSystem` per GPU; PhysX never splits one system across devices. Prefer one process per GPU for throughput (Isaac Lab / `torchrun` / `jax.distributed` layout: a rank that sees only its own GPU, e.g. through `CUDA_VISIBLE_DEVICES`, keeps `PhysxGpuSystem()`; when all GPUs stay visible, rank `r` passes `PhysxGpuSystem(f"cuda:{local_rank}")`, because the default `"cuda"` does not follow `torch.cuda.set_device()`). In one process, create one system per device (each device gets its own PhysX CUDA context manager, like omni.physx `sceneMultiGPUMode`), build and `gpu_init()` all of them from one thread, then drive each from its own thread: every steady-state call (step, fetch, apply, compute, query, `wait_idle`, `close`) releases the GIL, non-indexed applies return without blocking the host (indexed overloads synchronize once for their index check while `gpu_index_validation` is on), and calls into one system from several threads are serialized. Stepping all systems from one thread needs `PhysxSceneConfig.cpu_workers >= 1` and `step_start()` on every system before any `step_finish()`; fetch/apply raise in between, and it is the slowest layout. Keep each system's CUDA buffers, index buffers, `copy_from` sources and `gpu_set_cuda_stream()` stream on its device; cross-device inputs raise. `wait_idle()` waits only for the system's own stream. SAPIEN calls restore the caller's current CUDA device, so never rely on them to select the device for Torch. See the multi-GPU section of `docs/gpu-workflows.md`.
18. Multi-GPU rendering follows the PhysX layouts: pair each device's `PhysxGpuSystem` with render systems and one `RenderSystemGroup` on the same device. Choose a render device only through `RenderSystem(device)`; `sapien.render.SapienRenderer()` takes no device. One process per GPU: a rank seeing only its GPU keeps `PhysxGpuSystem()` and `RenderSystem()` (both pick that GPU although Vulkan enumerates all); with every GPU visible pass the same `f"cuda:{local_rank}"` to both. One process: create each device's render systems on that device (`sapien.render.RenderSystem("cuda:k")`) and one group per device, build everything and call every `gpu_init()` on one thread, then drive each device's step/fetch/`update_render()`/`take_picture()` from its own thread (they release the GIL; calls into one group are serialized; groups on one device that share no render system may also run on separate threads). A group, window or VR display raises `RuntimeError` for render systems of another device, and windows/VR always use the default render device. Keep the group's `set_cuda_stream` stream equal to the PhysX system's (another device's stream raises). `take_picture()` overwrites the picture buffers after work already on the group's stream; a consumer on another stream (JAX) must be ordered there before the next `take_picture()`: `copy_from(action)` into a PhysX buffer does it when PhysX and the group share the stream, otherwise `RenderCameraGroup.gpu_wait_for(x)`. Materials, textures, cubemaps, meshes and loaded models are device-independent: share them across devices (each device uploads its copy lazily, also from several threads at once); edits reach every copy and are not ordered with renders in flight, so edit them and call `sapien.render.clear_cache()` only while no thread renders. Camera-group CUDA outputs are on the group's device. GPU-written render buffers are per device: `RenderCudaMeshComponent(..., device=...)` fixes its device at construction, point-cloud CUDA arrays follow their scene's device, and `RenderShapeTriangleMeshPart.get_cuda_vertices/get_cuda_triangles(device=None)` export the copy of the given device. See the multi-GPU rendering section of `docs/gpu-workflows.md`.

## Joint friction and corrected setup behavior

- Joint `friction`, `set_friction`, `set_joint_frictions`, builder `friction`, and URDF dynamics friction use Coulomb effort: N for prismatic, N*m for rotational joints. Static and dynamic efforts are equal; values must be finite and non-negative; the default is 0.05 (builder and URDF values left unset keep it) and zero disables friction. Do not reuse old dimensionless joint coefficient values as physically equivalent efforts. Material friction coefficients are unchanged. Configure before GPU initialization, or between completed GPU steps using the existing property-update path; never during an in-flight step. Clone/reparent preserves efforts.
- Before group sealing, attached lights propagate shadow enable, map-size, and texture edits, including resource invalidation; setup-only fields still raise after `RenderSystemGroup.gpu_init()`. An attached textured light rejects `texture=None` without mutation; detached lights accept it.
- Empty external `CudaArray` views accept null pointers and retain the source `__dlpack_device__` when available, otherwise the current CUDA device at import. Existing borrowed ownership and non-empty pointer checks remain unchanged.
- Orthographic camera bounds use the floating-point image aspect ratio. Convex collision clones preserve local pose/filter/density/offsets. Attached collision-shape pose edits raise before mutation; missing mesh files raise a descriptive RuntimeError. C++ triangle-mesh string literals select the filename overload, not SDF generation.

## Material and body configuration

- Before GPU `gpu_init()`, configure material `friction_combine_mode` /
  `restitution_combine_mode` and body `max_linear_velocity` / `max_angular_velocity`
  when needed. All have explicit `get_*`/`set_*` methods as well as properties.
- Combine modes are strict strings: `'average' < 'min' < 'multiply' < 'max'` in
  contact-pair priority. Friction combines static/dynamic coefficients independently;
  restitution is separate. Changes affect every shape sharing the material. Keep
  explicit material references; `get_default_material()` uses a weak cache, not
  persistent global mode defaults.
- Body limits accept finite float32 values in inclusive `[0, 1e16f]` and survive
  articulation clone/reparent. They limit COM speed magnitude and angular speed
  before solving, not each component or every post-step velocity. They are not
  joint DOF limits and do not cap kinematic targets; link limiting can change momentum.
- CPU writes are supported between completed steps; post-init GPU propagation is
  not guaranteed and no freeze guard is enforced. Never mutate during an in-flight
  step (for shared materials, this applies to all using scenes).

## Guardrails

- PhysX GPU heaps consume both device and pinned host memory. Do not deliberately exhaust VRAM by constructing giant-heap scenes: failed host-page pinning can leak RAM in affected kernel/driver stacks even after the process exits. The repository OOM test is opt-in (`SAPIEN_TEST_GPU_OOM=1`), uses one bounded 256 MiB scene heap with 128 MiB GPU headroom, and must run alone with a process timeout and host-memory limit. Test recovery in the same process, including teardown/recreate and independent CUDA allocations; restarting the process alone does not prove recovery.

- Do not mix CPU state APIs with GPU runtime state updates.
- Do not request raw `__cuda_array_interface__` export from owner-tracked SAPIEN outputs (`PhysxGpuSystem` CUDA buffers, `RenderSystem.cuda_object_transforms`, or `RenderCameraGroup` image/pose buffers); it raises because it cannot carry the lifecycle guard or the stream order. Use DLPack (`torch.from_dlpack(x)`, `jax.dlpack.from_dlpack(x)`, `.torch()`, `.jax()`, `.cupy()`, `.dlpack()`) and release the resulting consumers before closing the owner. This does not change external CUDA-array-interface objects accepted as indexed API inputs.
- Do not cache a JAX view of a SAPIEN buffer across fetches, donate arrays imported from SAPIEN to a jitted function, or bridge JAX results through a Torch view on an unrelated stream; re-export after each fetch and write back with `CudaArray.copy_from`.
- Do not call `sync_poses_gpu_to_cpu()` in normal Viewer, training, reset, step, sensor, video, or offscreen capture paths; it downloads all poses to CPU and is only appropriate for explicit CPU debugging or Viewer `cpu-debug`.
- Do not render manually restored articulation state after only `gpu_update_articulation_kinematics()`. That call invalidates the public link-pose rows; fetch them with `gpu_fetch_articulation_link_pose()` before `RenderSystemGroup.update_render()`, whose CUDA transform kernel reads the supplied `cuda_rigid_body_data` exactly and performs no implicit PhysX fetch.
- Do not use CPU pose setters on sealed/static components after `RenderSystemGroup.gpu_init()`: static-pose tampering (moving a `'static'`-mode camera, a `'static'`-mode light, a CPU-owned static body, point-cloud entity, or light entity) raises at `RenderSystemGroup.update_render()` (or the next `scene.update_render()` for entity-pose changes). `'cuda'`-mode cameras and `'cpu'`-mode cameras/lights are the only movable pose paths after `gpu_init()`; move cuda cameras through `cuda_poses`/`set_cuda_pose`, cpu cameras/lights through `set_local_pose`. Camera projection/intrinsics (fov, near/far, principal point, skew, perspective/ortho parameters) stay CPU real-time in every mode; the CUDA kernel writes only view/inverse-view so a projection change never overrides a GPU pose. Light color, spot inner/outer FOV, parallelogram shape, shadow near/far, directional shadow half-size, and ambient light stay CPU real-time after `gpu_init()`. Setup-only fields that raise after `gpu_init()`: shadow enable/disable, shadow map size, textured-light texture, `set_gpu_pose_batch_index`, and `set_scenes`; light count/type and scene membership stay frozen via the scene-version check. `scene.update_render()` plays no role in grouped capture. Move mounted cameras and all dynamic bodies (including those in implicitly discovered shared scenes) through their PhysX pose rows, and bind moving objects to a CUDA pose source. Do not call `update_render()`/capture before `gpu_init()` or create camera groups after it. Do not recreate `RenderCameraGroup` per frame; `BatchedRenderSystem` retains every created camera batch and would accumulate GPU/Vulkan resources.
- Do not bind app-specific interactive controls to SAPIEN viewer navigation keys such as `W/A/S/D/Q/E`; prefer non-conflicting keys such as `I/K/J/L` for planar commands, `U/O` for yaw, `C` to clear commands, and `N` to reset.
- Do not create batched rendering before render bodies/cameras have GPU pose batch indices.
- SAPIEN has no IK solver; `GpuInverseKinematicsSolver` and `gpu_inverse_kinematics` do not exist.
- Do not pass CPU, non-contiguous, non-`int32`, cross-device, or PhysX-internal GPU index buffers to indexed GPU APIs, and do not call fetch/apply between `step_start()` and `step_finish()` (they raise).
- Do not remove a grouped camera's entity to "pause" it: after `RenderSystemGroup.gpu_init()` the removal waits for in-flight GPU work, then the group's `update_render()`/`take_picture()` raise and the camera cannot rejoin a scene until the group is closed.
- Do not add a `RenderTexturedLightComponent` to a scene before setting its `texture`; the add raises.
- Do not apply all GPU buffers during normal step; apply only buffers modified in that step.
- Remember SAPIEN quaternion convention is `wxyz`.
- Do not ignore SAPIEN's `Failed to find Vulkan ICD file` warning in GPU containers; fix Vulkan/EGL ICD setup and verify `import sapien` is warning-free under `docker run --gpus ...`.
- Do not let containers rely on SAPIEN's runtime PhysX GPU download. `enable_gpu()` downloads `physxgpu-linux-clang.zip` into `$HOME/.sapien/physx/<version>/` when the library is missing; fresh containers do not persist that writable layer, so this repeats and can fail offline. Pre-bake the extracted library into the image, or mount a persistent volume at the runtime user's `$HOME/.sapien`.
